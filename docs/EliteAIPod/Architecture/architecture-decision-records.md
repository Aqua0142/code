## ADR-001 — Use PostgreSQL pg_trgm GIN Index for ILIKE Medication Name Search

**Status:** accepted

**Context:** The sub-500ms search latency NFR requires fast case-insensitive partial name matching across the medications table. Standard PostgreSQL ILIKE queries without an index perform full sequential scans which, while acceptable for <1,000 rows today, would degrade as the dataset grows. The search must trigger on 3+ character queries, meaning prefix-only indexes are insufficient.

**Decision:** Enable the pg_trgm PostgreSQL extension and create a GIN trigram index on the medications.name column. This reduces ILIKE query execution to <50ms even on larger datasets by pre-computing character trigrams, leaving ample headroom within the 500ms end-to-end budget.

**Alternatives considered:**
- Full-text search (tsvector/tsquery) — better for natural language but overkill for medication name matching; trigram is more appropriate for arbitrary substring search
- Application-level search (in-memory filtering) — only viable with very small datasets; not a sustainable pattern as inventory grows
- Elasticsearch — significant operational overhead for a simple single-field search on a small dataset
**Consequences:**
- pg_trgm extension must be installed in the PostgreSQL instance (CREATE EXTENSION pg_trgm)
- GIN indexes have higher write overhead than B-tree; acceptable for this read-heavy, low-write workload
- Index size is larger than B-tree; negligible for <10,000 medication records
- Queries with 1-2 characters bypass the trigram index and fall back to sequential scan; mitigated by enforcing min 3-char query length at the API layer

## ADR-002 — Network-Level Access Control as Sole Authentication Mechanism

**Status:** accepted

**Context:** The system handles ePHI (medication inventory data) and must comply with HIPAA security requirements. However, the PRD explicitly states the application will be deployed on a secure internal network, and no user-level authentication was scoped into the user stories. Implementing JWT auth without a user story requirement would over-engineer the sprint and add complexity with no approved scope.

**Decision:** Rely exclusively on network-level controls (VLAN isolation, firewall rules restricting access to pharmacy workstations only) as the authentication boundary. The application has no login screen, no session tokens, and no user identity management. TLS 1.2+ is enforced at the nginx reverse proxy layer to protect data in transit. This decision must be validated with stakeholders before go-live to confirm network controls are in place.

**Alternatives considered:**
- JWT-based authentication — adds login UX and token management complexity beyond approved sprint scope; no user story requires it
- IP allowlist at the application layer — redundant with firewall-level control and brittle to maintain in application code
- OAuth2/SSO integration — appropriate for future sprints if the application scope expands beyond the internal pharmacy network
**Consequences:**
- Any device on the internal VLAN can access medication data — requires strong network perimeter controls
- A compromised internal device represents a full data exposure risk; mitigated by encryption-at-rest and network monitoring
- Go-live gate must include explicit confirmation from IT/security that network controls are configured
- Future sprints may add user-level auth as the security posture evolves
_Related: NFR-security-tls, NFR-security-encryption_
## ADR-003 — React Query for Async State Management in the Search SPA

**Status:** accepted

**Context:** The search UI requires three distinct async states — loading, success (with data), and error — as well as debounced queries, automatic refetch on input change, and accessible announcements via aria-live. These concerns span component state, network calls, and accessibility requirements (US-004). A custom useEffect + useState approach is error-prone and verbose.

**Decision:** Use TanStack React Query (v5) for all server state management in the SPA. React Query provides built-in loading/error/success state discrimination, automatic request deduplication, and query key-based cache invalidation. Debouncing is implemented with a custom hook wrapping useDeferredValue or setTimeout, feeding into a React Query useQuery call enabled only when query length >= 3.

**Alternatives considered:**
- Redux Toolkit Query — heavier boilerplate, RTK is more appropriate for complex multi-domain state not present in this single-search-feature SPA
- SWR — similar to React Query but less feature-rich error handling and no built-in enabled flag for conditional queries
- Vanilla fetch in useEffect — requires manual loading/error state management, cache management, and race condition handling; high maintenance burden
**Consequences:**
- Adds @tanstack/react-query as a frontend dependency (~14KB gzipped)
- Provides consistent loading/error/empty state discrimination out of the box, directly satisfying US-004
- The query key includes the search string, so cache hits eliminate redundant API calls for recently-seen queries
- Developers must follow React Query patterns (queryFn, staleTime, enabled flag) consistently across future features
_Related: US-001, US-004, NFR-performance, NFR-usability_
## ADR-004 — Modular Monolith Architecture for Single-Context, Low-Concurrency Application

**Status:** accepted

**Context:** The application has a single bounded context (medication inventory search), 1-10 concurrent users, and no inter-service communication requirements. The critical path spans database schema → API → frontend in a linear dependency chain, strongly suggesting a single deployable unit is appropriate.

**Decision:** Build the backend as a modular monolith with distinct layers (routes, services, repositories, models) enforced by Python package structure. This provides clear separation of concerns without the network latency, operational complexity, and distributed tracing overhead of microservices.

**Alternatives considered:**
- Microservices — unjustifiable operational overhead for a 1-10 user internal tool with one domain
- Pure monolith (no module separation) — acceptable for MVP but makes future extraction harder; the layered structure adds negligible complexity
**Consequences:**
- All code deploys as a single container; no independent scaling of sub-components
- Clear layer boundaries (routes → services → repositories → models) are enforced by code review convention, not runtime isolation
- Future decomposition into microservices is straightforward because domain boundaries are already explicit
_Related: US-001, US-002, NFR-performance, NFR-reliability_
