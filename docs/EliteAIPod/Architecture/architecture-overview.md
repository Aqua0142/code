## Architecture Pattern

**Pattern:** modular_monolith

A modular monolith is the optimal pattern for this pharmacy medication search SPA. The system has a single bounded context (medication inventory search), 1-10 concurrent users, and a sub-500ms latency NFR that is far easier to satisfy within a single process than across network hops. Microservices would add operational overhead with no benefit at this scale. The modular structure (routes → services → repositories → models) provides clear separation of concerns and enables future decomposition if the scope grows, without the distributed-systems complexity that would be premature here.

## Infrastructure

- **Deployment:** Docker Compose deployment on internal pharmacy server with HTTPS enforced via reverse proxy (nginx with TLS 1.2+ certificate). The MedicationSearchAPI and MedicationDatabase run as separate containers with a shared Docker network. Static frontend assets are served by nginx. Health checks and automatic container restart policies provide 99.9% availability during pharmacy operating hours.
- **Scaling:** Vertical scaling of the single server is sufficient for 1-10 concurrent users. The stateless FastAPI application supports horizontal scaling behind nginx if demand grows. PostgreSQL connection pooling via asyncpg handles concurrent queries. The pg_trgm index ensures query latency stays under 50ms even as the dataset grows to tens of thousands of records.
- **Caching:** none

## Security Considerations

- TLS 1.2+ enforced on all client-server communication via nginx reverse proxy; HTTP requests redirected to HTTPS
- PostgreSQL encryption-at-rest enabled using pgcrypto extension or OS-level filesystem encryption (LUKS) to protect ePHI medication data
- All database queries use SQLAlchemy parameterized statements to prevent SQL injection; query parameter validated and sanitized by Pydantic before reaching the repository layer
- Network-level access control: the application is deployed on an isolated internal VLAN accessible only to authorized pharmacy workstations; no public internet exposure
- Input length limits enforced at API layer (max 200 chars for q parameter) to prevent abuse
- No user credentials stored in the application; authentication deferred to network/infrastructure boundary controls
- Secrets (DATABASE_URL, TLS private key) stored in environment variables / secrets manager, never committed to source control
- Regular PostgreSQL backups encrypted at rest to protect ePHI in backup artifacts
